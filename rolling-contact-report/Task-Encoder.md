## Motivation

This project analytically computes the ZMP, CoM-velocity, and CoM-position
stability polygons under sustained contacts. The method is described in
<https://arxiv.org/abs/2308.06784>. A G1 example is:

```sh
./build/src/AreaCalculator --robot g1
```

The CoM-velocity area can quantify standing stability and, when future contacts
are included, the stability and force capability of a future stance. The
analytical calculation requires a robot model, idealized contacts, and an
assumed friction coefficient. Inspired by the local SONIC and HumanoidGPT paper
notes, this task distills the analytical calculation into a compact learned
representation suitable for batched simulation and policy rewards.

## Required outcome

Train an encoder-decoder with the following primary contract:

- Input: the G1's 29 actuated joint positions and 29 joint velocities.
- Output: an ordered, fixed-size approximation of the planar CoM-velocity-area
  vertices, in metres per second and counter-clockwise order.
- Supervision: labels generated by this repository's analytical C++
  implementation, never silently reused after a failed projection.
- Primary integration: ManiSkill 3 / SAPIEN with the official Unitree G1 robot.
- PPO validation: compare an otherwise identical G1 PPO task with and without a
  reward derived from the learned polygon.

Contact indicators and friction may be added as an explicitly named conditioned
model variant. They must not replace the required proprioception-only model.

## Planned additional contributions

These are optional and must be evaluated separately from the required model:

1. Contact/friction-conditioned prediction to expose analytical assumptions.
2. Convexity-aware decoding or projection with an invalid-polygon audit.
3. Predictive uncertainty and an out-of-distribution fallback to the analytical
   solver or a conservative polygon.
4. Active sampling near the learned stability boundary instead of uniform pose
   perturbations.
5. Future-contact conditioning for stance transitions and force-capability
   estimation.
6. Uneven-terrain transfer and simulator-to-simulator consistency checks.

## G1 dual-area training and worked-contact examples

The completed dual-head extension in `Task-DualAreaEncoder.md` uses one
proprioceptive encoder for both ZMP and CoM-velocity polygons. Its input is the
canonical 29-position plus 29-velocity vector. The network is a
`58 → 256 → 256 → 64` shared encoder followed by a ZMP decoder and a residual
CoM-velocity decoder, with 140,388 parameters in total. Both heads emit 16
counter-clockwise fixed-ray vertices.

The paired native generator attempted 228,003 G1 states and accepted 200,000;
28,003 failed or invalid paired projections were rejected. The frozen split is
140,000 train / 30,000 validation / 30,000 test. Every label used double-foot
support, friction coefficient 0.7, ZMP height 0 m, and 64 native LP directions.
Training used AdamW (`3e-4`, weight decay `1e-5`), batch 256, cosine decay,
seed 11, at most 500 epochs, and patience 40. The loss combined standardized
radial Smooth-L1 (`0.25`), normalized vertex error (`1.0`), relative area error
(`0.1`), and convexity penalty (`1.0`), with equal weight on both heads.

On the locked 30,000-state test split, both heads passed every frozen gate:
normalized vertex MAE was `0.14218` for ZMP and `0.14422` for CoM velocity;
relative area MAE was `0.03197` and `0.03208`; all predictions were finite,
convex, and counter-clockwise. The warmed TorchScript CPU batch-one median was
`450.4 us`.

The validation-only worked-example audit recorded on 2026-08-25 divides all
30,000 validation poses into equal near/middle/far perturbation tiers and picks
the all-contact-feasible row nearest each tier's median frozen-model score.
The selected dataset rows are 90,978, 15,858, and 81,692, with representative
double-foot scores `0.10067`, `0.11657`, and `0.13875`. Each figure shows the
DART-derived G1 configuration and native LP, fixed 16-ray target, and learned
ZMP/CoM-velocity polygons under left-foot, right-foot, and double-foot contact.

The model is not contact-conditioned: identical q/q-dot input produces the same
learned polygon in all three columns. Double foot is the only supported learned
context. The left- and right-foot native calculations demonstrate why runtime
guards must call the paired analytical solver for unsupported contacts; they
are not generalization claims. Double-foot plots use the frozen stored labels
that defined training and evaluation, while single-foot plots use the current
native solver at the archived float32 state. Current double-foot replay is
recorded separately because the archive stored q/q-dot after casting to float32.
