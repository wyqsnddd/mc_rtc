# Interactive rolling-contact control

> **Partly superseded.** Sections that describe the open-loop steering layer —
> the `keyboardYawScale` / `keyboardMixedDriveScale` wheel-rate calibrations,
> the `keyboardSteeringRate` slew, the `keyboardWheelPositionLookahead`, the
> drive-hold barrier and the command-transition grace period — record the state
> of the controller *before* the four-steering QP rate rows landed. Those knobs
> and the code behind them no longer exist: the steering and rolling rate
> references are now generated by `mc_rbdyn::steeringWheelReference` and
> arbitrated inside the QP, with `setCommandedTwist` as the single command entry
> point. Read those sections as history; `README.md` describes the current
> behaviour.

Status: implemented in the `RollingContact` sample controller and in
`config/mc_rtc-ranger-mini-v3-keyboard.yaml`. This document is the executable
acceptance checklist for the two interactive entry points:

1. the mc_rtc GUI/ticker command panel; and
2. the keyboard command path used by `mc_mujoco`.

The original issue mixed launch instructions, key bindings, and expected
motion without defining how to tell a working controller from a merely running
process. The steps below make each hand-off observable and give every claim a
validation or a test.

## 1. Scope and acceptance criteria

The controller is considered fixed only when all of the following are true.

- The exact graphical launch command starts the Ranger Mini V3 simulation and
  exposes a writable `Rolling Contact / Command` panel in `mc_rtc_ticker`.
- Editing **Forward velocity**, **Lateral velocity**, or **Yaw velocity** in
  that panel changes the corresponding logged reference on the next control
  cycle. **Clear command** returns all GUI and keyboard inputs to zero.
- From a real terminal, `W/S`, `A/D`, and `Q/E` produce signed forward,
  lateral, and yaw references respectively. A `W` interval makes
  `RollingContact_base_position_target_x` non-decreasing while W is active
  (within numerical tolerance); a `Q` interval makes the unwrapped
  `RollingContact_base_yaw_target` increase (it must not jump at `+/-pi`).
- `space` clears the latched axes but leaves keyboard capture running. `x`
  stops capture and clears both keyboard and GUI overrides, so no command can
  remain active after the stop key.
- Every logged control cycle has `RollingContact_solver_success=1`,
  `RollingContact_diagnostics_valid=1`, finite numeric fields, valid wheel
  measurements after the first sample, non-negative force/torque margins, and
  no unexplained `RollingContact_invalid_reason`.
- With `closedLoopFeedback: true`, the `FloatingBase` body-sensor packet is
  copied into both the control and real robot MBCs before the QP. The logged
  `RollingContact_base_pose/twist` therefore matches the measured
  `FloatingBase_*` pose/twist (within sensor/log precision), while the
  controller never writes a world-frame task reference into free-joint
  `alpha[0]`. A one-step QP prediction must not leak into the measured-state
  logs.
- The Ranger model uses one unambiguous chassis origin: the URDF link frame,
  chassis visual/collision origin, inertial origin, MuJoCo free-joint body
  frame, and `FloatingBase` sensor are coincident. The runtime
  `RollingContact_floating_base_chassis_error` must remain at numerical zero;
  the MuJoCo-only `chassis_frame` site is a visual marker at that same origin.
  This catches a model/frame rebase that would otherwise look like a control
  tracking error.
- The active rolling residual remains below `5e-3 m/s` in a straight
  forward/stop run. Steering alignment can produce a bounded, short-lived
  residual spike (keep it below `0.35 m/s` and record its maximum); after the
  command is cleared, both the residual and position tracking error
  (`RollingContact_base_position_tracking_error`) must be `<=1e-3` in the
  final 1 s (200 samples at the 5 ms timestep).
- Controller time remains below the 5 ms period at the 99th percentile. A
  longer transient during steering alignment is acceptable only if it settles
  and no solver cycle fails; a persistent residual, failed solve, or negative
  margin is a failure.
- Holding a translation key together with Q or E changes the instantaneous
  centre of curvature without getting stuck: W+Q and W+E must both keep all
  four wheels in `rolling`, keep `RollingContact_contact_fallback=0`, and
  produce measured radii within the configured tolerance. Validate at least
  two radius ratios, including the checked-in `0.6 m` profile and an alternate
  profile (the procedure below uses `1.2 m`). The bounded transition residual
  may reach `0.35 m/s`, but the steady interval must be below `0.05 m/s`.
- Changing an active yaw command to a lateral or forward command is a bounded
  transition, not a contact failure. The exact no-clear sequences Q→A, Q→W,
  E→A, and E→W must keep `RollingContact_solver_success=1`, leave
  `RollingContact_contact_fallback=0`, keep all estimated wheel modes
  `rolling`, and cap measured chassis speed at the configured command plus a
  small transient margin. During the hinge slew the rolling kinematic rows
  may be deactivated for at most the configured `0.5 s` grace interval; the
  physical dynamics/contact cone remains active.

For the requested `mc_mujoco` launch, physical yaw is mandatory: the checker
reconstructs chassis yaw from `FloatingBase_orientation_*` (the MuJoCo free
joint quaternion), verifies that Q produces positive and E negative motion,
and checks the measured rate against the 0.5 rad/s keyboard reference. A
reference target that moves while the chassis turns the wrong way is a failure,
even when every QP solve succeeds.

## 6. Step 3 — keyboard forward, lateral, and safe-stop test

Start fresh runs from a real terminal with the checked-in configuration (or
the temporary GUI-disabled copy for headless validation). Exercise one axis at
a time so each log identifies the hand-off. First run the strict forward test:

1. press `w` and leave it latched for at least 2 s;
2. press `space` and wait at least 1 s;
3. press `x`, wait for one controller poll, then terminate the simulator with
   Ctrl-C.

Then run a second log for lateral motion, pressing `a` for at least 1 s and
then `d` for at least 1 s before repeating the `space`/`x` stop sequence. A
third fresh run can combine all keys for a manual usability check, but it is
not the strict residual/convergence artifact.

The expected log transitions are:

| Action | Required evidence |
| --- | --- |
| `w` | positive `RollingContact_reference_linear_speed`; `base_position_target_x` never decreases between consecutive samples while W remains active (the first sample after `space`/`x` may re-latch the measured pose) |
| `s` | negative `RollingContact_reference_linear_speed` |
| `a` / `d` | opposite signs in `RollingContact_reference_lateral_speed` |
| `space` | all reference speeds become zero while `RollingContact_keyboard_steering_ready` remains valid |
| `x` | `RollingContact_keyboard_running` becomes `0`; `RollingContact_keyboard_status` has all axes at zero (also returned by `RollingContact::GetKeyboardStatus`); GUI overrides are zero and wheel targets stop changing |

For a strict residual check, make the first run W-only (`w`, wait, `space`,
wait, `x`) and convert its newest binary log. Replace `LOG` and `CYCLES` with
the paths/count printed by the run:

```sh
build/utils/mc_bin_to_log LOG /tmp/keyboard.csv
python3 rolling-contact-report/scripts/check-controller-log.py LOG \
  --cycles CYCLES --scenario keyboard --backend Tasks \
  --utils build/utils --residual-limit 5e-3 \
  --output /tmp/keyboard-report.json
```

Run the A/D sequence as a second smoke run. Its steering-alignment samples may
have a transient residual above the straight-run limit. Run the checker with
`--residual-limit 0.2` for this run to validate schema, finite values, solver
status, and margins, and retain its reported maximum; the final-second
assertion below still uses the strict `5e-3 m/s` limit. This records the
transient instead of hiding it by changing the acceptance criterion. Inspect
the converted A/D CSV (for example `/tmp/keyboard-ad.csv`) with a short script
or spreadsheet; use that path in place of `/tmp/keyboard.csv` below. The
following invariants are deliberately simple and should be retained if this
test is automated later. Replace `AD_LOG` and `AD_CYCLES` with the second
run's binary-log path and cycle count:

```sh
build/utils/mc_bin_to_log AD_LOG /tmp/keyboard-ad.csv
python3 rolling-contact-report/scripts/check-controller-log.py AD_LOG \
  --cycles AD_CYCLES --scenario keyboard --backend Tasks \
  --utils build/utils --residual-limit 0.2 \
  --output /tmp/keyboard-ad-report.json
```

The snippet below is for the W-only CSV. For A/D, replace the input path and
retain the final-tail, solver, and stop assertions; the W-target assertion is
not applicable to a lateral command.

```python
import csv
```

```python
rows = list(csv.DictReader(open("/tmp/keyboard-q.csv"), delimiter=";"))
```

The yaw checker performs the physical checks that cannot be inferred from the
reference alone. It unwraps the logged quaternion yaw, fits the measured rate
after the steering-alignment transient, and requires Q/E to be within
`0.1 rad/s` of `+/-0.5 rad/s`. It also requires the closed-loop
`RollingContact_keyboard_yaw_error` to settle below `0.15 rad`, all solver and
diagnostic flags to remain valid, and the final 200 samples after `x` to have
zero yaw error and zero keyboard axes. If this script fails, retain both the
binary and converted logs; do not substitute the monotonic target check.

## 8. Step 5 — mixed turning-radius test

This is the regression for the former “W+Q becomes stuck” failure. Start one
fresh TTY run with the checked-in profile (`keyboardLinearSpeed=0.3`,
`keyboardAngularSpeed=0.5`, expected radius `0.6 m`) and issue the following
latched-key sequence, waiting at least 2 s after each mixed command has been
entered:

1. press `w` (straight reference warm-up);
2. press `q` (W+Q, counter-clockwise physical turn);
3. press `space`, then `w`, then `e` (W+E, clockwise physical turn at the
   same radius); and
4. press `x`, wait for the capture-stopped banner, and terminate with
   Ctrl-C.

The space key is important: keyboard commands are latched because a terminal
supplies key-down bytes rather than key-release events. Translation keys clear
the yaw axis, while Q/E add yaw to the current translation; therefore W+Q and
W+E still exercise mixed-radius motion, but Q/E followed by W/A is a true
translation command rather than an unintended circle. Convert the
resulting binary log and run:

```sh
build/utils/mc_bin_to_log MIXED_LOG /tmp/keyboard-qe-radius.csv
python3 rolling-contact-report/scripts/check-keyboard-radius.py \
  /tmp/keyboard-qe-radius.csv --expected-radius 0.6 --radius-tolerance 0.15 \
  --expected-rate 0.5 --rate-tolerance 0.1 --residual-limit 0.35 \
  --output /tmp/keyboard-qe-radius.json
```

Repeat the same sequence with a temporary copy whose translation/yaw ratio is
different. Do not edit the checked-in production profile; this example keeps
the linear speed at `0.3 m/s` and changes the yaw reference to `0.25 rad/s`,
so the expected radius is `0.3 / 0.25 = 1.2 m`:

```sh
ALT_CFG=$(mktemp --suffix=.yaml)
cp rolling-contact-report/config/mc_rtc-ranger-mini-v3-keyboard.yaml "$ALT_CFG"
sed -i 's/Enable: true/Enable: false/; s/keyboardAngularSpeed: 0.5/keyboardAngularSpeed: 0.25/' "$ALT_CFG"
/home/yuquan/local/bin/mc_mujoco --without-visualization \
  --without-mc-rtc-gui -s -f "$ALT_CFG"
build/utils/mc_bin_to_log ALT_LOG /tmp/keyboard-qe-radius-1p2.csv
python3 rolling-contact-report/scripts/check-keyboard-radius.py \
  /tmp/keyboard-qe-radius-1p2.csv --expected-radius 1.2 \
  --radius-tolerance 0.25 --expected-rate 0.25 --rate-tolerance 0.06 \
  --residual-limit 0.35 --steady-residual-limit 0.05 \
  --output /tmp/keyboard-qe-radius-1p2.json
rm -f "$ALT_CFG"
```

The alternate-radius run is a required independent check, not an optional
demonstration. Both profiles must show a Q interval and an E interval of at
least 2 s, opposite measured yaw signs, a radius inside its own tolerance,
all wheels in `rolling`, zero contact fallback, and a final 1 s position/yaw
error and rolling residual within the stop limits. Scaling the complete wheel
rate (rather than only its yaw component) is what preserves this ratio while
the steering geometry changes.

The checker reconstructs the physical quaternion yaw, converts the MuJoCo
world linear velocity into the body frame used by RBDyn, and fits each steady
W+Q/W+E interval after its one-second steering transient. It requires positive
Q and negative E rates, forward body speed, `|v_x/omega_z|` near `0.6 m`, all
solver/diagnostic flags valid, all wheel modes still `rolling`, no contact
fallback, no residual above the bounded `0.35 m/s` transition limit, and a
steady-state residual below `0.05 m/s`. A
mixed run that merely keeps the process alive while the wheel modes are
`sliding` or `detached` is a failure, even if the reference fields look right.

The mixed path deliberately scales the complete wheel-rate magnitude with
`keyboardMixedDriveScale` (1.15 in the checked-in profile). Scaling only the
yaw component changes the steering angle and therefore changes the requested
radius. Pure Q/E retains the separate `keyboardYawScale` calibration.

### Step 5a — no-clear yaw-to-translation transition regression

The roll-away report did not clear Q/E before pressing A or W. Run a fresh TTY
session and hold each sequence for at least 2 s after the second key is
observed:

1. press `q`, then press `w` without `space`;
2. press `x` and wait for the capture-stopped banner;
3. repeat in a fresh run with `q`, then `a` without `space`;
4. repeat in fresh runs with `e`, then `w`, and `e`, then `a`.

For each converted CSV, locate the first row where the second axis appears and
inspect the next 100 samples (the 0.5 s grace window). The following checks
are mandatory:

```python
import csv
rows = list(csv.DictReader(open("/tmp/transition.csv"), delimiter=";"))
assert rows
for row in rows:
    assert row["RollingContact_solver_success"] == "1"
    assert row["RollingContact_diagnostics_valid"] == "1"
    assert row["RollingContact_contact_fallback"] == "0"
    for wheel in ("front_left", "front_right", "rear_left", "rear_right"):
        assert row[f"RollingContact_{wheel}_mode"] == "rolling"
def axes(status):
    return {token.split(":")[0] for token in status.split() if token.endswith(":1")}
transition = next(i for i in range(1, len(rows))
                  if (axes(rows[i - 1]["RollingContact_keyboard_status"]) & {"Q", "E"})
                  and not (axes(rows[i - 1]["RollingContact_keyboard_status"])
                           & {"W", "A", "D", "S"})
                  and (axes(rows[i]["RollingContact_keyboard_status"]) & {"W", "A", "D", "S"})
                  and not (axes(rows[i]["RollingContact_keyboard_status"]) & {"Q", "E"}))
assert max(float(row["RollingContact_keyboard_transition_grace"])
           for row in rows[transition:transition + 100]) <= 0.5 + 1e-9
assert rows[transition]["RollingContact_keyboard_status"].split(" Q:")[1].startswith("0 E:0")
assert abs(float(rows[transition]["RollingContact_reference_yaw_rate"])) <= 1e-12
ready = next(i for i in range(transition, len(rows))
             if rows[i]["RollingContact_keyboard_steering_ready"] == "1")
for row in rows[transition:ready]:
    assert all(abs(float(row[f"RollingContact_{wheel}_rate"])) <= 1e-12
               for wheel in ("front_left", "front_right", "rear_left", "rear_right"))
assert max(abs(float(row["FloatingBase_linearVelocity_x"]))
           for row in rows[transition:transition + 100]) < 0.6
assert max(abs(float(row["FloatingBase_linearVelocity_y"]))
           for row in rows[transition:transition + 100]) < 0.6
assert max(abs(float(row["FloatingBase_angularVelocity_z"]))
           for row in rows[transition:transition + 100]) < 0.6
tail = rows[-200:]
assert max(float(row["RollingContact_base_position_tracking_error"]) for row in tail) <= 1e-3
assert max(abs(float(row["FloatingBase_linearVelocity_x"])) for row in tail) <= 1e-3
assert max(abs(float(row["FloatingBase_linearVelocity_y"])) for row in tail) <= 1e-3
assert max(abs(float(row["FloatingBase_angularVelocity_z"])) for row in tail) <= 1e-3
```

The grace counter is logged specifically so a one-cycle ordering regression
cannot hide behind a successful process exit. The measured base twist is read
from the real robot; it must not jump to a task's commanded free-joint alpha
when the steering representation changes. `RollingContact_keyboard_steering_ready`
is the four-hinge barrier: every drive rate must remain zero until it becomes
`1`, even if the bounded 0.5 s command grace has already elapsed. This is what
prevents the asymmetric Q/E-to-A/D impulse that previously made the Ranger roll
away rapidly.

## Resolution and remaining regressions (2026-09-06)

The steering issue that motivated this document — WASD/QE commands responding
badly on the four-steering Ranger — was traced to a structural gap in the QP,
not to gains. The steering axis passes through the wheel centre, so steering
produces no translation of the wheel centre; because the QP's rolling rows came
only from the carrier *translational* Jacobian, the steering joint had an
identically zero column in every QP row. The QP could not plan steering at all,
so the controller steered open-loop through the posture task and needed the
empirical compensations this document catalogues: the yaw sign mirror,
`keyboardYawScale = 1.7`, `keyboardMixedDriveScale = 1.15`, the branch-cut
hysteresis, the "don't spin while steering" gate and the transition grace
period.

The plan that carried out the fix is
[`plans/2026-09-05-four-steering-wheel-qp.md`](plans/2026-09-05-four-steering-wheel-qp.md).
It adds a rotating-rate block to the four-steering QP (four rolling rates and
four steering rates), an affine rate prediction, rate-tracking objective terms
and rate bounds; inverts the expanded steering constraints into per-wheel
references via `mc_rbdyn::steeringWheelReference`; and deletes the open-loop
layer. `rolling-contact-qp.tex` is the corrected theory the implementation now
matches (the superseded revision is kept as `rolling-contact-qp-old.tex`).

**What is fixed.** The steering column is no longer zero: for a `+0.6 rad/s`
steering-rate reference the optimal steering acceleration goes from exactly `0`
to `0.597 rad/s^2` (Tasks) / `1.481 rad/s^2` (TVM), each matching its closed
form. All six pure-axis commands are exact mirrors through the assembled
controller (forward `dx=+0.5929`, backward `-0.5929`, crab-left `dy=+0.5353`,
crab-right `-0.5353`, yaw+ `dyaw=+0.9186`, yaw- `-0.9186`). Through the full
ticker path at `v=0.15 m/s`, `omega=0.25 rad/s`, forward/reverse/crab/pure-yaw
and Ackermann-left all reproduce the commanded motion over 5 s. The full mc_rtc
regression is 104/104. The empirical scale factors are gone.

**What is not fixed — this issue is NOT closed.**

1. `scenario: ackermann_right` (twist `(0.15, 0, -0.25)`) stalls in the
   kinematic ticker: front-left and rear-right go `detached` at cycle 2 and stay
   detached for 781 of 1000 cycles, the rate references are zeroed while
   detached, and the chassis advances `0.042 m` instead of `0.75 m`. The
   mirrored `ackermann_left` is clean for all 1000 cycles, and the per-wheel
   references at cycles 0 and 1 are exact mirrors of each other, so the
   asymmetry is inside the QP and the contact-mode logic rather than in the
   reference inversion. The pre-rewrite controller (`dff9cc26f1`) is symmetric
   on the same command (`dx=+0.5197`, `dy=-0.2997`, `dyaw=-1.0467`, zero
   detached cycles), so this is a regression of the rate-row controller.
2. In closed-loop CPU MuJoCo, `four-crab` and `four-ackermann-left` fail on both
   backends (drive torque saturated at the 35 Nm actuator limit, minimum normal
   force `0`, contact-fallback sample fraction 0.93-0.95, peak rolling slip
   0.22-0.66 m/s). `four-forward` and `four-pure-yaw` pass on both backends. All
   four cases pass on both backends with the pre-rewrite controller.

No unit test covers a mixed forward-plus-*negative*-yaw command; adding one is
the first step of the follow-up. Note that the tracked
`evidence/mujoco-summary.json` predates the Ranger Mini V3 model and is not a
valid numerical baseline for it — the comparisons above were made by rebuilding
the pre-rewrite controller against the current model, not by reading that file.

## Task 0 — whole-body carry-over of the R2 normal-load argument (2026-09-07)

`rolling-contact-qp-corrected.tex` (`sec:planar-normal-load`) argues, in the
*planar* 3-DOF reduction, that (1) every reduced contact-Jacobian column is
tangent to the ground (`n_Π^T J_red,i = 0`), so a purely normal force does no
generalized work; (2) with the symmetric 4-generator basis, `C_i·1 ∝ n_i`, so
`λ_i ↦ λ_i + s·1` (`s ≥ 0`) preserves every constraint and every objective
term while inflating the normal force without bound — the friction cone is
vacuous along that ray; and (3) the normal kinematic row consequently reduces
to `0 = 0` and must not be appended, replaced by an exogenous
`n_Π^T C_i λ_i = f^ref_{n,i}` row. `plans/2026-09-07-revised-four-steering-qp.md`
Task 0 required checking whether (2)/(3) hold in mc_rtc's actual **whole-body**
QP over `alphaD`, where the floating base has a vertical DOF, before deciding
whether to carry the remedy over (Task 4, R2/R3).

**Method.** A throwaway `BOOST_AUTO_TEST_CASE` was appended to and then
reverted out of `tests/testRollingContactSolver.cpp` (Tasks backend, the
existing `loadFourSteeringRobot()`/`fourSteeringWheels()`/`ackermannTarget()`
fixtures already used by `RollingTasksFourSteeringAckermannTargetWithDynamics`).
No diagnostic code was committed; see the confirmation at the end of this
entry.

**Measurement 1 — does the `λ* + s·1` ray survive the whole-body QP?**
Built the four-steering QP with `RollingContactDynamicsConstraint` (equations
of motion + torque bounds, via the native `tasks::qp::MotionConstr`) and
`RollingContactConstraint` attached, solved an Ackermann target
(`linear=0.15`, `yaw=0.05`, `|alphaD - target| = 1.67e-4`), then perturbed the
solved λ* by `+s` on all 8 generator multipliers of every wheel simultaneously
(`s ∈ {0, 1, 10, 100}`):

- Premise confirmed exactly: for all four wheels, the sum of the 8 unit
  generator columns (`normalize(n + mu·t_k)`, 2 endpoints × 4 generators) is
  exactly parallel to that wheel's normal direction — `cos(angle) = 1` and
  `|C_i·1| = 6.55386` identically for every wheel (matches
  `8/sqrt(1+0.7^2)` analytically). The paper's cone-shape premise holds
  bit-for-bit in mc_rtc's actual Tasks generator basis.
- `motionConstr()` is 14 rows × 46 cols: 6 unactuated floating-base rows
  (`Lower == Upper`, the EOM equalities) + 8 actuated drive/steer torque-bound
  inequalities, over 14 `alphaD` + 32 `lambda` (4 wheels × 8) columns.
  Baseline (`s=0`) residual on the 6 EOM rows is `2.84e-14` (solver noise
  floor).
- At every tested `s > 0` the ray is killed, immediately and linearly, by
  **one single EOM row**: row 5 of the unactuated block (the floating base's
  vertical/z-translation row, per the `ackermannTarget` dof convention
  `target(2)=yaw(wz)`, `target(3)=linear(vx)`, i.e. `[wx,wy,wz,vx,vy,vz]`).
  Violation: `s=1 → 26.2154`, `s=10 → 262.154`, `s=100 → 2621.54` — exactly
  linear in `s` (coefficient `26.215421456609363`), not a threshold effect.
  The actuated-joint torque-bound rows (6–13) show **zero** violation at every
  tested `s`. Tracing the geometry: this wheel model has zero camber/caster,
  so the contact point sits directly along the terrain normal from both the
  drive and the steering joints' reference points, giving a zero lever arm
  for a purely-normal force about either axis. That is a property of this
  wheel geometry, not a general guarantee, and it is **not** the mechanism
  the theory anticipates (which is the equations of motion, not actuation
  limits) — so it does not weaken the finding.
- `minLambda` stayed positive and grew with `s` (`8.19 → 9.19 → 18.19 →
  108.19`): generator non-negativity is trivially preserved for `s ≥ 0`,
  exactly as expected.
- `objectiveDelta = 0` and `kinematicResidualDelta = 0` exactly at every `s`
  (alphaD is untouched by a lambda-only perturbation, and no current mc_rtc
  objective term reads `lambda`) — the theory's "leaves every objective term
  unchanged" clause is *also* exactly true today, but only because the
  Tikhonov term (R3) does not exist yet; it will break this invariance once
  implemented, which is one reason to implement it regardless of the Task 0
  outcome.

The floating-base EOM equality rows are not optional or soft — they are
present whenever `RollingContactDynamicsConstraint` is attached — so this is
not a case of the ray being killed only by some incidental constraint.

**Measurement 2 — do the normal kinematic rows carry rank in whole-body
coordinates?** Built `RollingContactConstraint` directly (no solver
registration needed; `hardMatrix()`/`hardRowLabels()` are populated by the
constructor) with `steeringPlanar=false` (all four wheels contribute a hard
lateral row) at two steering configurations, each with `constrainNormal`
true/false, and computed rank with both `Eigen::FullPivLU` (threshold `1e-9`)
and `Eigen::JacobiSVD` (explicit `1e-9·sigma_max` cutoff) — the two methods
agreed exactly in all four cases:

| Configuration | `constrainNormal` | rows | rank | singular values (rounded) |
| --- | --- | --- | --- | --- |
| Coordinated (common-ICR Ackermann, `linear=0.15`, `yaw=0.05`) | false | 8 | 6 | 2.010, 2.000, 1.087, 0.2, 0.198, 0.169, ~0, ~0 |
| Coordinated | true | 12 | 9 | 2.010, 2.000, 2.000, 1.087, 0.9, 0.6, 0.2, 0.198, 0.169, ~0, ~0, ~0 |
| Not coordinated (`front_left=+0.30, front_right=-0.10, rear_left=+0.20, rear_right=-0.30` rad, no common ICR) | false | 8 | 7 | 2.009, 2.001, 1.088, 0.2, 0.199, 0.155, 0.044, ~0 |
| Not coordinated | true | 12 | 10 | 2.009, 2.001, 2.000, 1.088, 0.9, 0.6, 0.2, 0.199, 0.155, 0.044, ~0, ~0 |

Appending the 4 normal rows raises rank by exactly **+3** — not 0 and not
+4 — in *both* the coordinated and the non-coordinated configuration. This is
a consistent, non-ambiguous result across two structurally different steering
states. (Secondary, unprompted observation: both configurations are already
rank-deficient *before* the normal rows are even considered — 6/8 and 7/8 —
which is the pre-existing, already-documented redundancy of stacking all four
wheels' exact lateral rows under near-Ackermann steering, the same
over-determination `RollingContactConstraintOptions::steeringPlanar`'s doc
comment already names; it is orthogonal to the normal-row question. The
+3-not-+4 pattern for the normal rows themselves is consistent with the
classical kinematic redundancy of four coplanar unilateral contacts on one
rigid body — three independent height/tilt constraints, one redundant — but
that reading was not separately derived in this session, only observed to be
numerically consistent, so it is offered as an interpretation, not a proven
mechanism.)

**Decision.** Both measurements agree, unambiguously: no admissible ray (the
floating-base vertical EOM row kills it immediately, exactly, and via a
non-optional constraint), and the normal rows add real rank (+3 of +4, in
both tested configurations, never 0). Per the plan's Task 0 branches
(`plans/2026-09-07-revised-four-steering-qp.md` lines 99–100): **skip Task
4's normal-load row** (`n_Π^T C_i λ_i = f^ref_{n,i}`), **keep
`constrainNormal = true`** (already `RollingContactConstraintOptions`'s
default), and **implement only the Tikhonov `eps_lambda·||lambda_i||^2` half
of R3** (Hessian conditioning on the `λ` block, needed regardless of this
decision). `sec:planar-normal-load`'s vacuous-cone / `0=0`-row argument in
`rolling-contact-qp-corrected.tex` is a planar-reduction artifact that does
**not** carry over to mc_rtc's whole-body QP: the cone-shape premise
(`C_i·1 ∝ n_i`) is confirmed exactly, but the conclusion drawn from it is not,
because the floating base's vertical-translation DOF gives `n^T J_i ≠ 0`
(confirmed: it is exactly the row that kills the ray) where the reduced
3-DOF model has that projection annihilated by construction.

## Task 1 — whole-body carry-over of assumption A1 (`as:planar-basis`) (2026-09-07)

`rolling-contact-qp-corrected.tex` (`sec:planar-qp-assumptions`, `as:planar-basis`)
requires every planar quantity to be resolved in the **chassis-aligned** basis,
so that the wheel offsets `rho_i` and the planar wheel maps `H_i` are constant
and `Hdot_i = 0` drops out of the differentiated rows. An earlier reading of
this assumption flagged `mc_rolling_contact_controller.cpp:391` — the world
`UnitX` projected off the terrain normal — as the violation. That reading is
wrong on both counts, and acting on it would have broken the controller.

**Claim (a) — `rho_i` is already chassis-frame and constant.** `wheelOffsets_`
is built once, in the constructor, at
`mc_rolling_contact_controller.cpp:279-281`:

    const Eigen::Vector3d worldOffset =
        robot().frame(wheel.carrierFrame).position().translation() - chassis.translation();
    wheelOffsets_.push_back((chassis.rotation() * worldOffset).head<2>());

`sva::PTransformd::rotation()` is `E_0_c`, the world-to-chassis map, so
`chassis.rotation() * worldOffset` is the offset expressed in the chassis
frame. That is exactly `rho_i` in the chassis-aligned basis A1 asks for, and it
is what `mc_rbdyn::steeringWheelReference()` consumes. Verified by measurement,
not only by reading: `PlanarWheelOffsetsAreChassisHeadingInvariant`
(`tests/testRollingContactRobot.cpp`) places the Ranger at yaw
`0, pi/4, pi/2, -2pi/3` and finds the chassis-frame offsets drift by
`2.78e-17` across the sweep, while the same offsets read in the world-fixed
basis drift by `0.235 m` (smallest pair over the sweep; largest `0.531 m`).

**Claim (b) — the whole-body rows carry no `H_i`, hence no dropped `Hdot_i`.**
`RollingContactGeometry::update` (`src/mc_rbdyn/RollingContact.cpp:366-369`)
builds its three rows as `dir^T * carrierJacobian` for the inertial-frame
rolling/lateral/normal directions, minus `radius * spinSign * wheelSelector` on
the rolling row. There is no planar `H_i` factor anywhere in that product. The
time dependence of those rows is carried by `accelerationBias`
(`:376-381`) as `dir . carrierNormalAcceleration + dirRate . carrierVelocity`,
where `carrierNormalAcceleration` is RBDyn's `normalAcceleration()`, i.e.
`Jdot * alpha` at the carrier center. `Gdot * alpha` is therefore exact, not
approximated, and there is no `Hdot_i` term being dropped.
`ResolvedRollingBiasMatchesMatrixDirectionalDerivative` already pins this
against a finite-difference of `G(q) * alpha` to `1e-5`.

**Why `terrainTangentX_` / `terrainTangentY_` must stay world-fixed.** Those
two vectors are not the planar row basis; they are the **yaw reference frame**.
They are consumed at `mc_rolling_contact_controller.cpp:1003, 1109, 1166, 1292,
1545` as

    measuredYaw = std::atan2(measuredHeading.dot(terrainTangentY_), measuredHeading.dot(terrainTangentX_));

and at `:1208-1211` to build the trajectory `heading`/`side` vectors. If that
basis rotated with the chassis then `measuredHeading . terrainTangentX_` would
be identically `1` and `measuredHeading . terrainTangentY_` identically `0`, so
`measuredYaw` would collapse to zero and `baseYawTarget_`, the closed-loop
keyboard heading and the trajectory frame would all silently break. A
world-fixed yaw reference is a requirement, not an oversight, and A1 does not
speak about it.

**Decision.** A1 is already satisfied in substance by the whole-body
implementation; it requires **no** change of basis. GEO-01
(`PlanarWheelOffsetsAreChassisHeadingInvariant`) and GEO-02
(`ChassisAlignedPlanarBasisIsOrthonormalRightHandedAndBodyConstant`) are
committed as regression **pins** on that existing behaviour. Both are
non-vacuous by construction: each computes the world-fixed variant of the same
quantity alongside the chassis-aligned one and asserts the two disagree, so a
regression to a world-fixed `rho_i` fails them. Confirmed by mutation as well —
substituting the world-fixed expression for the chassis-frame one makes both
report a drift of `0.531` against their `1e-12` bound; the mutation was
reverted.

**GEO-03 and the one behaviour change.** The basis construction moved into
`mc_rbdyn::planarContactBasis(normal, forward)`
(`include/mc_rbdyn/RollingContact.h`, `src/mc_rbdyn/RollingContact.cpp`), which
throws `std::invalid_argument` when `forward` is parallel to `normal` instead of
normalizing what round-off leaves behind. The controller now selects its
forward axis (world `UnitX`, falling back to `UnitY`) and hands it to that
helper, so the fallback keeps its existing behaviour for every reachable input
and gains the guard. Honest caveat: with the world-axis pair the
degenerate-against-both branch is **unreachable** for a unit normal, since it
would need `n_x^2 > 1 - 1e-16` and `n_y^2 > 1 - 1e-16` at once, i.e.
`n_x^2 + n_y^2 > 1`. For the controller the guard is therefore defensive. It is
load-bearing — and directly tested by
`DegenerateForwardAxisAbortsThePlanarBasis` — for callers that pass their own
forward axis, which is precisely how the chassis-aligned basis of A1 is built
in GEO-02.

the pre-task baseline. This task added tests and one guard; no existing number
moved.
