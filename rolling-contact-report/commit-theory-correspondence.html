1. The one-paragraph version

The revised \eqref{eq:four-steering-wheel-qp} makes five changes to the four-steering QP. One of them was real for this codebase — softening the four lateral rows with per-wheel slacks — and it is the change that actually fixed the robot. Three were measured not to transfer from the planar reduction to mc_rtc's whole-body QP, and implementing two of them literally would have broken working code. The remaining one (a matrix twist weight) mapped onto machinery mc_rtc already had. The single most consequential line of evidence: with hard lateral rows and non-ICR-coordinated steering, the QP produces identically zero planar acceleration even at 10× demand — a rank fact, not a tuning artefact.

3. Corrections that deliberately did not carry over

This is the most important section for anyone re-reading the theory against the code. Four corrections in the planar document are correct there and wrong — or vacuous — in mc_rtc's whole-body QP. Each was settled by measurement, not argument. Implementing two of them literally would have broken working code.

R2 — normal-load row eq:planar-normal-load-row (tex:1091) not carried over

Recorded in 2bfe66aa85. The planar argument is that nΠᵀ Jred,i = 0 (eq:reduced-normal-annihilated, tex:1067) makes the friction cone vacuous via the ray λ → λ + s·1, and the normal kinematic row identically 0 = 0.

Measured in whole-body form: the cone-shape premise holds exactly — Ci·1 ∥ ni, cos = 1, |Ci·1| = 6.55386 = 8/√(1+0.7²) — but the ray is killed linearly by the floating base's vertical equation-of-motion row: violation 26.2154 per unit s, and that row is not optional. The normal kinematic rows add rank +3 in both coordinated and non-coordinated configurations, so they are not 0 = 0.

Consequence: constrainNormal stays true and no normal-load row is imposed. Adding one would fight gravity and over-constrain the QP.

A1 — chassis-aligned basis as:planar-basis (tex:1151) already satisfied

Recorded in 596036df3d. ρi and Hi are objects of the planar reduction. wheelOffsets_ is already chassis-frame and constant (drift 2.78e-17 across yaw {0, π/4, π/2, −2π/3}, where a world-fixed basis drifts 0.235–0.531 m), and the whole-body rows have no Hi at all — the Jacobian's time dependence is carried exactly by normalAcceleration() = J̇·α.

Danger: an earlier draft of this work proposed rebuilding terrainTangentX_ from the chassis forward axis. That would have been catastrophic — those vectors are the world-fixed yaw reference, and chassis-aligning them makes measuredYaw = atan2(0, 1) ≡ 0, silently zeroing every yaw measurement.

R3 — Tikhonov term eq:planar-force-regularization kept, defaulted off

33c7bdc137 added it; 1f136644ad defaulted it to 0.0. The theory's premise is that the generators appear in no motion objective, leaving the Hessian singular on the λ block. Measured: the smallest Hessian eigenvalue at ε = 0 is 1e-4 — positive, because the Tasks backend applies an unconditional DIAG_CONSTANT diagonal floor. The solver already prevents the singularity.

At ε = 2e-4 the term biased solved tangential force by 0.008936 N on 2.17860 N (41% of a 1% budget) and degraded four-steering tracking 1.67e-4 → 6.692e-4.

But note: a later measurement found ε ≥ 0.2 does fix an unrelated problem — the four-coplanar-contact load-distribution null space — giving 177/181/187/190 N with no tracking cost. So the term is useful for load-distribution selection, not for Hessian conditioning. The option is retained for solvers without a diagonal floor.

DYN-02 — the Ṗu term does not transfer

RBDyn's floating-base alpha is already the body twist, so P is constant along planar motion and Ṗ ≡ 0 exactly (measured 0; a probe returns 0.80 on a tilting chassis, confirming the probe works). The card's content transfers as “the bias must be the full h(q,α), not gravity alone”, asserted at 640× the tolerance.

The general rule, and the single most useful takeaway from this branch: a correction derived from nΠᵀ Jred = 0 or from Ḣ = 0 is a statement about the reduction's coordinates. Check it against the whole-body form before implementing it.

5. Risks and fishy issues

A. The validation oracle was weaker than it looked — and its replacement still disagrees with reality

The CPU-headless MuJoCo suite was this project's primary validation signal and reported 8/8 green for weeks while being structurally incapable of observing a real bug: it injected MuJoCo ground-truth contact data every substep, which masked the controller reading its own solver's arbitrary load-distribution choice as if it were a contact sensor. Real mc_mujoco detached a wheel within 25 ms on cases the suite passed.

It also hard-coded torque_control: true while mc_mujoco defaults to false. ORC-08 measured the consequence: on a crab manoeuvre real mc_mujoco delivers 67.9% of the commanded distance under --torque-control versus 98.6% under joint PD — and the gap does not converge with timestep (0.2953 / 0.2151 / 0.2914 m at 5 / 2.5 / 1 ms, non-monotone across a five-fold refinement).

Status: cbd32acee7 makes the suite record its regime (--torque-control, --measured-contacts, --preset-steering) so the divergence is visible, and c2269e44f6 adds the real-mc_mujoco cross-check. The disagreement itself is unresolved. Treat CPU-suite green as necessary, not sufficient.

B. “107/107” is not trustworthy without a full rebuild and the right environment

Three independent ways the gate lies:

  • Stale version header (corrected — this was previously described here as version-string skew, which is wrong). src/CMakeLists.txt:83-92 generates include/mc_rtc/version.h with DEPENDS ${MC_RTC_ALL_FILES} — the tracked source list, not .git/HEAD. A bare git commit therefore touches no source mtime, the custom command does not rerun, and nothing rebuilds. The header goes stale (reporting the previous SHA), it does not go mixed — every binary stays uniformly stamped, so the *_CHECK_VERSION guards do not fire. Cosmetic for provenance, not a correctness hazard. Remove build/include/mc_rtc/version.h and rebuild if you need the stamp to match the commit.
  • Missing env var. MC_RTC_DISABLE_CONVEX_GENERATION_PATCH=ON must be exported for the whole ctest run, not just the rolling tests, or 49 JVRC1-loading tests crash in qhull (QH6028 … Wrong qh_fprintf was called).
  • Link-layout fragility. PrimalSolutionIsUniqueAcrossWarmStartsAndSolversQP03 passes in isolation (gap 1.05e-07 against a 2.2e-03 bound) but has failed in full-binary runs with a gap of 0.64. Its pass/fail tracks the link layout, not the source.
  • Concurrency. Running mc_mujoco or a second build alongside ctest produces cascades (libmc_rtc_utils.so.2: file too short, IPC socket collisions).

Practical rule: full rebuild, env exported, nothing else running — then trust it. The two large cascades actually observed (24 and 49 failures) are attributable to the missing env var and to concurrency, not to the version header; both cleared on a clean re-run.

C. Four separate checks were found passing vacuously. Assume there are more.

  1. The CPU MuJoCo suite (risk A) — could not observe the bug it was guarding.
  2. ORC-02 — its ICR-coordinated fixture makes the rolling-row bias identically zero (1.39e-17 vs 0.188 on an uncoordinated state), so a mutation deleting the entire bias term passed unnoticed. Now pinned by an explicit assertion.
  3. QP-03 — shared the same degenerate fixture (ICR angles at zero velocity). Fixing it improved Tasks/TVM agreement from 1.7e-6 to 1.0e-7.
  4. check-keyboard-yaw.py — bounded the yaw error only from above (< 0.15 rad), which a dead-zero signal satisfies trivially. It could never have caught the bug it existed to guard.

Every testcard added after this discovery is mutation-verified. Anything written before it should be treated as unverified until mutated.

E. Tuning against the kinematic ticker has caused a regression once already

The ticker has no contact physics. driveAcceleration was widened 20→100 on ticker metrics (lateral slip 0.291 → 0.079 m/s) while the same measurement recorded crab start-up friction margin collapsing from +70.6 to 0.0. In MuJoCo that setting saturated drive torque at the 35 Nm limit, zeroed normal force and detached wheels. Reverted in be199de66a.

The same trap nearly recurred with lateralSlackWeight: ticker-only tuning would have chosen 1e9 and shipped a MuJoCo failure. Use MuJoCo as the arbiter for anything touching contact.

F. Early commits are not independently buildable

0602969f8d and dff9cc26f1 are “chore” commits capturing pre-existing uncommitted working-tree state (the Ranger description and aliases; the controller, ticker configs and MuJoCo runner). They were added because 868009e5b9's tests referenced a robot alias that did not yet exist in-tree, and because the controller rewrite needed a reviewable diff. Commits before 0602969f8d will not build or test standalone, and those two bundle work not authored as part of this branch.

G. Config surfaces that exist but do nothing

RollingContactDescription::activation was parsed from YAML, validated, and documented in the JSON schema with a default of 1 — and never read. activation: 0.5 was silently ignored. Fixed in 7cad0dd7a5.

That is a pattern worth auditing, not a one-off: a schema entry plus a validator plus a doc comment is not evidence that anything consumes the value. Grep for a reader before trusting a config key.

J. A latent mc_mujoco trap that hides the entire robot

Every geom in ranger_mini_v3.xml is group 0 (no group attribute); only the terrain uses group="1". With no ~/local/share/mc_mujoco/mc_mujoco.yaml — today's state — layers 0/1/2 are on and the robot draws. The moment that file exists, visualize.collisions resolves to false and the vehicle vanishes, leaving only contact markers. mc_mujoco writes that file itself when GUI settings are saved. Reproduced exactly; the fix is group="1" on the robot's visual geoms, not applied.

K. Rendering fix needed a second pass — worth knowing why

ce7c96f0d8 correctly shrank scale.* (which multiply stat.meansize, 1.539 on ramps vs 0.131 flat) but also halved map/force — which divides by stat.meanmass, and that is 7.5 in both scenes because the terrain body is massless. It additionally sized for 184 N/wheel when MuJoCo's cylinder-plane collider emits two contacts per wheel (~92 N each). Net 4× too short. Corrected in 9e0e40f3f9.

The physics was never wrong: at rest the eight normal forces sum to 735.7500 N against m·g = 735.7500 N, residual −0.0000 N.
